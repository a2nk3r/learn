Why LLM Outputs Break Assertions

Page 1.1 named the problem. This page shows it failing in code: three assertion styles misjudging four answers, a sampler that turns one prompt into a distribution, the arithmetic of why one green run proves little, and the testing techniques software engineering already built for programs with no single correct output.

1.2.1Three assertions, four answers

Ask a model What is the capital of France? and suppose it returns one of the four outputs below. Three are correct; the fourth is wrong. Now grade them with the three assertions an engineer reaches for first: exact equality, equality after normalizing case and punctuation, and a substring check.

Table 2. Verdicts from assertions_demo.py (§1.2.5) against the reference "Paris". A ✗ marks a verdict that disagrees with the truth. The outputs are written for this demonstration, not sampled from a model.

Read the columns as two failure modes you already know from testing. exact and normalized produce false negatives: they reject two correct answers because the characters differ. contains produces a false positive: it accepts an answer that says the opposite, because the word it looks for is present.

Tightening the check trades one error for the other. No string rule on this page fixes both, because the property you care about is meaning, and meaning is not a property of the character sequence alone. The rest of the course replaces equal to with three better questions: how close to a reference (Part 2), how good according to a rubric (Part 3), and how often across many inputs and runs (Part 4).

1.2.2One prompt, a distribution of outputs

A language model does not compute an answer; it computes, at every step, a probability for each possible next token, then a decoder picks one. The final layer turns a vector of scores (logits) zi into probabilities with a softmax, usually scaled by a temperature T, written by Hinton et al. as:⁠[1]

qi= exp(zi/T) ∑jexp(zj/T) (1)

where qi is the probability of token i and T is normally set to 1. A higher T produces a softer, flatter distribution; as T approaches 0 the probability mass concentrates on the highest-scoring token, which is greedy decoding.

Deeper: why T→0 becomes greedy

Let zmax be the largest logit and assume it is unique. Divide the numerator and denominator of (1) by exp(zmax/T):

qi= exp((zi−zmax)/T) ∑jexp((zj−zmax)/T) (1′)

For every token other than the maximum, zi−zmax<0, so its term goes to 0 as T→0+. The maximum's own term is exp(0)=1, so its probability goes to 1. With a tie for the maximum, the mass splits evenly among the tied tokens instead. Inference engines special-case an exact 0 instead of dividing by zero; vLLM, for example, documents that a temperature of zero means greedy sampling.⁠[9]

Most decoders also truncate the distribution before sampling. Nucleus (top-p) sampling, from Holtzman et al., keeps the smallest set of tokens V(p) whose probabilities reach p, then renormalizes over that set and samples from it:⁠[2]

∑x∈V(p) P(x∣x1:i−1)≥p (2)

An output is a sequence of these draws, and each draw conditions the next. So one prompt defines a probability distribution over whole outputs, and one run of your feature is one sample from it. As §1.1.1 showed, even greedy decoding is not reliably reproducible on production servers, so that holds at temperature 0 too.

1.2.3Why one green run proves little

Suppose each run of a test case fails with probability f, and runs are independent. Then the chance that n runs all pass is:

P(all n runs pass)=(1−f)n (3)

With a 5% failure rate, a single run passes 95% of the time. To give yourself a 95% chance of seeing at least one failure, you need 0.95n≤0.05, so n≥ln0.05/ln0.95≈58.4: that is 59 runs.

Turn it around. If you ran a case n times and saw zero failures, the one-sided 95% upper bound on its failure rate solves (1−pu)n=0.05:

pu=1−0.051/n≈3n (4)

The approximation uses −ln0.05≈2.996 and is known as the rule of three.⁠[3] It is close for large n: at n=59, the exact bound is 0.0495 and 3/n is 0.0508.

So 59 green runs only let you claim, at 95% confidence, that the failure rate is below about 5%. One green run tells you almost nothing about a 5% failure. The model behind both formulas is a coin with a fixed bias: independent runs and a constant failure probability. Response caching, fixed seeds, or a model update between runs break that model, which is one reason Part 4 treats eval results as estimates with intervals.

1.2.4Testing without an oracle

Software engineering met this problem long before LLMs. Barr et al. survey the ways testers automate an oracle: modelling, specifications, contract-driven development, and metamorphic testing. When none of these is adequate, the final source of oracle information remains the human.⁠[4] Three of those ideas carry straight into evals.

Property-based testing

QuickCheck⁠[5] and Python's Hypothesis⁠[6] assert a property that must hold for every input, not one expected value. Language output has many properties you can check exactly, whatever the wording: it parses as JSON, matches a schema, cites only document IDs it was given, stays under a length limit, contains no email addresses. These become Part 2's deterministic checks.

Metamorphic testing

Chen, Cheung, and Yiu proposed checking a relation between the outputs of related inputs when no single output can be verified.⁠[7]⁠[8] For an LLM feature: a paraphrased question should get the same answer; shuffling the order of retrieved passages should not change the answer; adding an irrelevant sentence to the prompt should not flip a classification. There is a catch the original technique did not face: deciding whether two language outputs are the same itself needs a metric or a judge.

The human oracle

Human judgment does not disappear; it moves. You spend it on labeling a sample and on calibrating automated graders against those labels, which is error analysis (page 1.4) and judge validation (Part 3).

Reproduce Table 2 and the 59-run result on your own machine. The script uses only the Python standard library, so no virtual environment is needed yet; Lab 2 sets one up.

  1. Create the file

    Run these from the evals-lab folder you created on page 1.1.

  2. Copy in the script
    evals-lab/part1/assertions_demo.pyPython 3
    """Page 1.2: why string assertions misjudge language output."""
import math
import random
import re

# Part A: one question, four model outputs, three assertion styles.
REFERENCE = "Paris"
OUTPUTS = [
    ("Paris", True),
    ("The capital of France is Paris.", True),
    ("It's Paris.", True),
    ("The capital of France is not Paris.", False),
]


def exact(text: str) -> bool:
    return text == REFERENCE


def normalized(text: str) -> bool:
    clean = re.sub(r"[^a-z0-9 ]", "", text.lower()).strip()
    return clean == REFERENCE.lower()


def contains(text: str) -> bool:
    return REFERENCE.lower() in text.lower()


CHECKS = {"exact": exact, "normalized": normalized, "contains": contains}

print(f"{'output':<38}{'truth':<7}" + "".join(f"{n:<12}" for n in CHECKS))
for text, truth in OUTPUTS:
    row = f"{text:<38}{'ok' if truth else 'WRONG':<7}"
    for check in CHECKS.values():
        verdict = check(text)
        mark = "pass" if verdict else "fail"
        if verdict != truth:
            mark += " ✗"
        row += f"{mark:<12}"
    print(row)

for name, check in CHECKS.items():
    fn = sum(1 for t, ok in OUTPUTS if ok and not check(t))
    fp = sum(1 for t, ok in OUTPUTS if not ok and check(t))
    print(f"{name:<11} false negatives: {fn}   false positives: {fp}")

# Part B: a 5% failure rate hides behind a single green run.
FAILURE_RATE = 0.05
random.seed(7)
runs = 10_000
green = sum(random.random() >= FAILURE_RATE for _ in range(runs))
print(f"\nsingle runs that pass: {green / runs:.1%}")

n = math.ceil(math.log(0.05) / math.log(1 - FAILURE_RATE))
print(f"runs needed for a 95% chance of seeing at least one failure: {n}")

exact_bound = 1 - 0.05 ** (1 / n)
print(f"0 failures in {n} runs -> 95% upper bound: {exact_bound:.4f} (rule of three: {3 / n:.4f})")
