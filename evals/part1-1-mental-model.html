Mental Model Foundations

You already run an evaluation practice; you call it testing. This page maps the four tools of AI evaluation onto four tools you use every week, then marks exactly where each mapping stops being true. Read it before you write any eval code: the analogy tells you what each technique is for, and the breaks tell you what it cannot do.

1.1.1What changes when the output is language

A unit test works because the code under test has an oracle: for an input x you know the expected output y, so assert f(x) == y is decidable. Barr et al. call the absence of such a mechanism the test oracle problem, and survey how testing proceeds without one.⁠[2]

LLM features sit inside that problem. A summary, an answer, or an agent's plan can be correct in many surface forms and wrong in subtle ones. An equality assertion rejects a good paraphrase and accepts nothing else, so it tells you almost nothing.

Two more properties change. First, outputs are sampled: at a temperature above zero the same prompt is meant to produce different completions. Second, even greedy decoding at temperature 0 is not reliably reproducible on production inference servers. He and Thinking Machines Lab trace much of this to kernels that lack batch invariance: a request's numerics depend on how many other requests share its forward pass.⁠[3] The practical consequence for this course: an eval result is a measurement over a sample, not a single boolean.

Deeper: why temperature 0 still varies

Floating-point addition is not associative: (a + b) + c can differ from a + (b + c) in the last bits. He shows that this alone does not make a kernel nondeterministic; the same matrix multiplication on the same data repeatedly returns bitwise-equal results.⁠[3]

The missing piece is batch invariance. Common kernels change their reduction strategy with batch size, so one request's numerics depend on how many requests share its forward pass. In He's words, the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies.⁠[3] A tiny numeric difference can flip one greedy token choice, and every later token follows from it.

1.1.3The pyramid still applies

Mike Cohn's test automation pyramid argues for many more low-level tests than broad-stack ones. As Fowler summarizes, the pyramid rests on the assumption that broad-stack tests are expensive, slow, and brittle compared with focused tests such as unit tests.⁠[5] The same economics hold for evals. Run heuristic checks on every output. Spend judge calls only on qualities heuristics cannot assess. Reserve human review for the two jobs nothing else can do: labeling data and calibrating the judge.

Golden datasets are not a layer. They are the fixtures every layer runs against, just as one regression suite feeds the same fixtures to unit and integration tests. Vibe checks sit outside the pyramid entirely, like a debugger session: useful, never a gate.

1.1.4Where the bridge breaks

Analogies speed up learning and then mislead you at the edges. Keep these four corrections next to Table 1; each one is the reason a later Part exists.

Errata to the analogy

  1. There is no single expected value. Without an oracle,⁠[2] expected becomes a reference output, a rubric, or a human label. Every metric in Part 2 is a different answer to how close is close enough?
  2. Green once is not green. Because inference is not reliably deterministic,⁠[3] one passing run proves little. Run each case several times and report rates with confidence intervals (Part 4).
  3. The test can be wrong. An LLM judge carries measurable biases.⁠[1] Shankar et al. also observe criteria drift: users need criteria to grade outputs, but grading outputs helps users define criteria.⁠[4] So you read outputs before writing criteria; that is error analysis, later in Part 1.
  4. A passing suite describes the sample, not production. Your golden set is evidence about the inputs you collected. Users send other inputs; online evals (Part 4) close that gap.

## Where the analogy breaks for this feature

- Oracle: is there one right answer, or many acceptable ones?
- Determinism: have you seen one input produce two answers?
- Judge risk: which quality would a model grade unreliably?
- Coverage: which real user inputs are missing from your examples?
